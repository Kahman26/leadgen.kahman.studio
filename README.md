# Сборщик лидов — ниша бронирования, Екатеринбург

Веб-сервис, который сам находит отели, базы отдыха, бани, глэмпинги и посуточные
квартиры в городе, проверяет их сайты и складывает в базу **с готовым поводом для
звонка** по каждому лиду.

Главный критерий отбора: **сайта нет вообще** либо **сайт устарел / плохо сделан**.

---

## Быстрый старт

```bash
pip install -r requirements.txt
python -m uvicorn app:app --host 127.0.0.1 --port 8765
```

Открыть <http://127.0.0.1:8765> → кнопка **«Запустить сбор»**.

В Windows можно просто запустить `start.bat`.

---

## Как это работает

```
1. Сбор        OpenStreetMap (Overpass) — объекты ниши по bbox города
               Dadata (ЕГРЮЛ)          — компании ниши по ОКВЭД, с ИНН и директором
               Ручной импорт CSV       — любой список, который принёс маркетолог

2. Склейка     компании из ЕГРЮЛ подклеиваются к объектам с карты по названию,
               а не дублируют их

3. Аудит       каждый сайт проверяется обычным HTTP-запросом:
               жив ли, HTTPS, адаптив, движок, как устроено бронирование,
               год копирайта, скорость, whois домена

4. Контакты    телефон → Telegram → ВКонтакте → WhatsApp → почта
               берутся из тегов OSM и со страниц сайта (главная + контакты)

5. Скоринг     главный признак + список пробелов + заготовка первой фразы + балл 0–100

6. Работа      маркетолог фильтрует, звонит, ставит статус и пишет заметку
               попытки дозвона считаются сами — по смене статуса
```

### Почему источники именно эти

| Источник | Статус | Почему |
|---|---|---|
| **OpenStreetMap** | ✅ основной | Лицензия ODbL — данные можно легально хранить и использовать |
| **Dadata / ЕГРЮЛ** | ✅ дополняющий | 10 000 запросов в сутки бесплатно, даёт ИНН, ОКВЭД и ФИО директора |
| Яндекс.Карты API | ❌ не используем | Лицензия прямо запрещает хранить результаты (кеш максимум 30 дней) |
| 2ГИС API | ⚠️ платный | Бесплатного доступа нет с 01.08.2021, цены по запросу на api@2gis.ru |
| Парсинг их сайтов | ❌ не используем | Нарушение условий использования |

## Признаки, по которым лид попадает в базу

| Код | Признак | Балл |
|---|---|---|
| `SITE_DEAD` | Сайт не открывается | 55 |
| `NO_SITE` | Сайта нет вообще | 50 |
| `NO_MOBILE` | Нет мобильной версии (нет meta viewport) | 30 |
| `CHEAP_BUILDER` | Сделан на Wix / uKit / uCoz / Nethouse и т.п. | 18 |
| `OUTDATED` | Копирайт старше 3 лет | 16 |
| `NO_BOOKING` | Ни брони, ни заявки — только телефон | 20 |
| `REQUEST_ONLY` | Бронь только через заявку с обратным звонком | 12 |
| `NO_HTTPS` | Нет HTTPS | 10 |
| `SLOW` | Главная грузится дольше 3 секунд | 8 |

Баллы складываются, максимум 100. Есть телефон `+10`, Telegram или WhatsApp `+5`,
ВКонтакте `+3`. Нет ни одного контакта — `−30`: такой лид маркетологу бесполезен.

Порог «горячего» лида — 60 (`scoring.HOT`). Откалиброван так, чтобы в него попадал
объект с реальной проблемой **и** живым контактом: нет сайта (50) + телефон (10).

Веса меняются в [scoring.py](scoring.py). После правки — кнопка
**«Только пересчитать баллы»** в диалоге сбора: пересчёт идёт по сохранённым
данным, сайты заново не обходятся.

**Главным** признаком в карточке становится самый болезненный из найденных —
именно с него начинается разговор.

Отдельный статус `BLOCKED` — сайт закрыт Cloudflare и подобной защитой.
Такие в «мёртвые» не попадают: звонить с «у вас сайт лежит», когда он жив, нельзя.

### Сверка с ЕГРЮЛ

Каждый лид сверяется с реестром через Dadata: статус организации, ИНН, ОГРН,
ФИО руководителя, ОКВЭД, юридический адрес, дата регистрации.

Сложность в том, что на карте названия торговые («Паровозов», «Черника»),
а в ЕГРЮЛ компания называется иначе, и однофамильцев в городе десятки.
Поэтому совпадение принимается не по названию, а по сумме независимых
подтверждений:

| Подтверждение | Баллы |
|---|---|
| Название совпадает точно | +3 |
| Название совпадает частично | +1 |
| ОКВЭД из ниши (55, 68.20, 96.04, 93.29, 79) | +2 |
| Улица и дом совпадают с адресом на карте | +3 |
| Юр. адрес в Екатеринбурге | +1 |

Совпадение названия и города само по себе не принимается ни при каком балле:
нужен **профильный ОКВЭД или совпавший адрес**. Иначе «Уралэлектромедь»
цепляется к одноимённому заводу, а «Лайнер» — к любому ООО «Лайнер» в городе.

**6 и больше** — берём как есть. **4–5** — сохраняем с пометкой «совпадение
неточное, проверьте», в карточке видно, чем именно подтверждено. **Меньше 4** —
не сохраняем вообще: чужой ИНН в карточке хуже, чем пустое поле.

Статус «ликвидирована» обнуляет балл **только при высоком доверии**. При неточном
совпадении лид остаётся в работе, а в «чего не хватает» появляется предупреждение:
иначе живой объект вылетит из списка из-за закрывшегося однофамильца.

Если ИНН уже известен, данные берутся точным запросом по нему — там гадать не о чем.

**Ликвидированные компании** получают балл 0, отдельный признак и зачёркнутую
плашку. Их видно фильтром «Организация: ликвидированные» — дальше можно скрыть.

Чего Dadata не даёт: **сайт, телефон и почту** — на обычном тарифе эти поля пустые.
Сайты по-прежнему берутся из OpenStreetMap и проверяются своим аудитом.

### Как разбирается бронирование

Для отеля разница между «забронировал сам» и «оставил заявку» — это деньги,
поэтому состояний три:

| `booking_type` | Что значит | Как определяется |
|---|---|---|
| `engine` | Гость бронирует сам | Найден движок (TravelLine, Bnovo, YClients, Островок, Суточно…) **или** на странице есть поля выбора дат заезда и выезда |
| `request` | Гость оставляет заявку, менеджер перезванивает | Форма с телефоном или именем, виджет заявки (Битрикс24, JivoSite, Envybox, Marquiz…), либо кнопка «оставить заявку» / «заказать звонок» |
| `none` | Ни того, ни другого — только телефон | Ничего из перечисленного не найдено |

Важная тонкость: одного слова «забронировать» на кнопке недостаточно —
чаще всего за ней обычная форма заявки. Настоящим бронированием считается
только то, где гость **сам выбирает даты**. Поэтому проверяются поля ввода,
а не текст: слова «заезд» и «выезд» есть почти на каждом сайте отеля
(«заезд с 14:00»).

Флаг `online_booking` оставлен для совместимости и равен 1 только для `engine`.

## Что показал первый реальный прогон по Екатеринбургу

Только OpenStreetMap, без Dadata. Bbox с пригородом, 13 сентября 2026.

**292 объекта ниши**, из них:

| Признак | Объектов | Средний балл |
|---|---|---|
| Нет сайта | 175 | 25 |
| Сайт в порядке | 44 | 14 |
| Сайт не открывается | 23 | 63 |
| Нет мобильной версии | 18 | 52 |
| Бронь только через заявку | 15 | 29 |
| Ни брони, ни заявки | 8 | 31 |
| Сайт устарел | 5 | 37 |
| Нет HTTPS | 4 | 25 |

Как устроено бронирование на 94 живых сайтах: **58** — настоящая система,
**20** — только заявка, **16** — ничего, кроме телефона.
Из движков: TravelLine 36, YClients 7, Bnovo 4, Островок 3, свои модули 7.

Контакты: телефон у 134, ВКонтакте у 54, Telegram у 23, WhatsApp у 16.

**Главный вывод — и он неприятный.** Объектов без сайта много (175), но телефон
есть лишь у 20 из них: OSM просто не заполнен. Работоспособный сегмент «нет сайта +
есть телефон» — это **20 лидов**, в основном бани и сауны.

А вот сегмент «сайт есть, но плохой» даёт **43 горячих лида** с контактами — и чек
там выше, потому что клиент уже один раз платил за сайт и понимает его ценность.

Отсюда два практических следствия:

1. Начинать обзвон стоит с фильтра «Сайт не открывается» и «Нет мобильной версии» —
   там средний балл 62 и 50, контакты почти везде.
2. Чтобы раскрыть сегмент «нет сайта», нужен токен Dadata: ЕГРЮЛ добавит телефон
   и ФИО директора там, где карта молчит.

Ещё одно ограничение: **посуточные квартиры в OSM почти не представлены** (5 объектов).
Они живут на Авито, Суточно и Островке. Для этого сегмента нужен либо Dadata
по ОКВЭД 68.20.1, либо ручной импорт CSV.

## Что хранится по каждому лиду

Полная схема — в [db.py](db.py). Ключевое:

- **Кто это** — название, категория, адрес, координаты
- **Откуда нашли** — `source` (`osm` / `dadata` / `manual`), `source_ref` (объект OSM или ИНН)
  и `source_detail` словами: «OpenStreetMap, тег tourism=hotel + ЕГРЮЛ (ИНН …)»
- **Откуда контакт** — `contact_source`, по каждому каналу отдельно:
  `{"phone": "сайт", "telegram": "OSM"}`
- **Почему записали** — `reason_code` + `reason_text`
- **Чего не хватает** — `missing`, список словами
- **Что говорить** — `pitch`, заготовка первой фразы
- **Работа маркетолога** — `status`, лента заметок, счётчики звонков

`status` и заметки при повторном сборе **не перезаписываются** — работа не теряется.

### Статусы

Порядок в списке и в фильтре повторяет реальный путь сделки, а не алфавит:

| Статус | Код | Что значит |
|---|---|---|
| Новый | `new` | Лид собран, к нему ещё не подходили |
| Автопроверка | `auto_checked` | Claude поискал по открытым источникам, человек ещё не смотрел |
| Ручная проверка | `in_work` | Человек посмотрел карточку и взял лид в работу |
| Не дозвонились | `no_answer` | Звонили, трубку не взяли |
| Связались | `contacted` | Поговорили с тем, кто принимает решение |
| Аудит | `audit` | Согласились на бесплатный аудит сайта |
| КП отправлено | `proposal` | Аудит и смета у клиента, ждём решения |
| Отказ | `refused` | Не интересно |
| Сделка | `deal` | Договор подписан, деньги пришли |

Статусы задаются словарём `STATUSES` в [app.py](app.py) — оттуда они сами
расходятся и в кнопки карточки, и в фильтр, и в журнал.

### Сделки и платежи

Раздел целиком закрыт для всех, кроме владельца базы: выручка и вознаграждение
продажника — не та информация, которую сам продажник должен читать по своему же
лиду. Продажник вместо блока видит одну строку «Сделка закрыта 17.09.2026»
без сумм, а денежные записи скрыты и в журнале карточки.

**Сделка** (`deals`) бывает двух видов:

- `project` — разовая разработка, `amount` это цена договора;
- `retainer` — абонентское ведение, `amount` это месячный платёж.

У сделки есть продавец (`owner_login`) — по нему считается вознаграждение —
и признак `is_repeat`: доработка, сопровождение, продвижение и наполнение
идут по другой ставке.

**Платежи** (`payments`) — фактические поступления с датой. Цена договора
и поступления разведены намеренно: по договору с продажником вознаграждение
считается от того, что **реально пришло**, а не от того, что подписали.
Источник правды для любых денежных расчётов — `payments`, а `deals.amount`
только план.

Суммы хранятся целыми рублями: деньги через плавающую точку считать нельзя,
копейки разойдутся на первой же сотне строк.

**Первый платёж закрывает лид.** По договору сделка считается закрытой в дату
фактического поступления первой оплаты, поэтому статус `deal` ставится сам,
и это пишется в журнал от имени того, кто внёс платёж. Обратно при удалении
платежа статус не откатывается: вернуть лид в работу — решение человека.

**Доля первой оплаты** считается от самого раннего по дате поступления, а не
по порядку ввода: платежи заводят задним числом. Если она меньше 30 %, в
карточке появляется пометка «не идёт в зачёт премии продажнику» — это условие
из договора, и о нём легко забыть при вводе.

У абонентки ни полосы выполнения, ни доли первой оплаты нет: делить поступления
на месячный платёж бессмысленно. Там показывается сумма и число оплаченных
месяцев.

Сделку можно удалить только пока по ней нет платежей — иначе история денег
исчезла бы молча. Список продавцов берётся из `LEADGEN_USERS`, отдельный
справочник заводить незачем.

### Заметки

Заметки лежат лентой в таблице `lead_notes`, а не одним полем: с базой работают
несколько человек, и в общем поле каждый затирал бы чужой текст. У записи виден
автор, время и цвет — тон считается из логина, поэтому один и тот же человек
всегда одного цвета, а новый сотрудник получает свой без правки кода.

Формат выбран так намеренно: цвет даёт мгновенное «это писал не я», ник отвечает
«кто именно», лента сохраняет хронологию разговора с клиентом. Группировка по
автору не подошла бы — важен порядок событий, а не кто больше написал.

Удаление мягкое (`deleted=1`): журнал изменений не должен ссылаться на
исчезнувшие записи. Свою заметку убирает автор, чужую — только владелец базы.
Редактирования чужих заметок нет вовсе.

Колонка `leads.note` осталась и работает зеркалом последней заметки — на неё
опирается выгрузка в CSV, где заметка выводится с ником автора в начале.

Заметки, которые были в базе до перехода на ленту, перенесены одной записью
на лид. Автор взят из журнала изменений — последняя правка поля `note`. Если
правки не нашлось, заметка старше журнала: такая помечена подписью
«перенесено из старой карточки», и автора ей не приписывают. Перенос отмечается
в таблице `meta` и повторно не запускается — признак «в таблице пусто» тут не
годится: человек мог удалить всё сам, и перенос вернул бы убранное.

### Журнал звонков

Продажник звонит, а трубку не берут — и это самый частый исход. Чтобы его было
куда записать, каждая попытка дозвона ложится в отдельную таблицу `calls`:
кто звонил, когда и чем кончилось (`no_answer` / `answered`).

Отдельная таблица, а не счётчик в лиде, нужна затем, что по ней считается
воронка и процент дозвона в разрезе сотрудников и периодов. В `leads` при этом
дублируются `call_count` и `last_call_at` — только ради того, чтобы список
рисовался одним запросом. Источник правды — `calls`.

Попытка пишется сама, нажимать лишний раз не нужно:

- перевод в **«Не дозвонились»** → попытка с исходом `no_answer`;
- перевод в **«Связались»** → попытка с исходом `answered`; пара этих
  чисел и даёт процент дозвона;
- кнопка **«Снова не ответили»** в карточке → ещё одна попытка, когда статус
  уже не меняется (`POST /api/lead/{id}/call`).

Повторный перевод в тот же статус попытку не создаёт: статус не изменился —
значит, и звонка не было.

Каждая попытка попадает в журнал изменений и читается как
«Пётр — звонок: не ответили». Отменить её нельзя: факт звонка откатывать
бессмысленно.

В карточке у «Не дозвонились» видно число попыток и время последней —
в часовом поясе города, хотя в базе лежит UTC. В остальных статусах остаётся
одна строка «Звонков: 3, последний 14 сентября»: когда лид уже перешёл
в «Связались», полезно понимать, сколько он стоил усилий. В списке число
попыток стоит рядом со статусом, и с третьей подсвечивается — по такому лиду
пора принимать решение, а не звонить дальше.

### Добавить объект руками

Кнопка **«+ Объект»** в шапке — если маркетолог нашёл кого-то сам. Обязательно
только название; сайт, телефон, Telegram, ВКонтакте, адрес и заметка
необязательны. Ниша по умолчанию — та, что открыта во вкладке; категорию можно
не выбирать.

При сохранении объект проходит тот же путь, что и собранные автоматически:
сайт проверяется аудитом, компания сверяется с ЕГРЮЛ, считается балл и признак.
Телефон приводится к общему виду, а с сайта дособираются контакты.

Перед добавлением идёт **проверка на дубликаты** — по домену и по названию.
Если объект уже есть, сервис откажет и назовёт его: заводить второй раз то,
что уже собрано с карты, смысла нет.

Адрес сайта помечается как заданный вручную, поэтому следующий сбор его
не перезапишет.

Для списка целиком есть **«Импорт CSV»** — колонки `name;website;phone;address;category;niche`.
Без колонки `niche` объекты попадают в нишу открытой вкладки. Незнакомые ниши
и категории из файла заводятся сами.

### Ниши и категории

Над таблицей — вкладки ниш с числом объектов: «Все» и восемь ниш —
бронирование и размещение, ремонт и строительство, авто, медицина и здоровье,
досуг и события, образование и спорт, услуги для людей и бизнеса,
интернет-магазины, — плюс те, что заведёт команда. Стартовый список ниш
и категорий — `SEED` в `niches.py`. Во вкладке
таблица, сводка, фильтр типов и выгрузка CSV показывают только эту нишу.
Открытая ниша живёт в адресе страницы (`/?niche=2`) — ссылкой можно
поделиться, кнопка «Назад» работает. В следующий раз откроется та же ниша.

У лида ниша обязательна, категория — нет. Выбираются они из двух списков
в форме объекта и в «Изменить» карточки. Последний пункт каждого —
«+ Новая ниша…» / «+ Новая категория…»: новая заводится вместе с объектом.
Название сравнивается без учёта регистра и «ё», поэтому «баня / сауна»
не создаст дубль «Баня / сауна».

Создавать может любой сотрудник. Раздел **«Ниши и категории»** в меню —
только владельцу базы: переименовать, объединить дубли (объекты переезжают),
поменять порядок вкладок, удалить пустое. Всё это пишется в журнал.
Сменённая руками категория защищена от сбора, как и другие ручные правки.

Сбор (OpenStreetMap и ЕГРЮЛ) пока настроен только под бронирование и кладёт
объекты в эту нишу. Если категорию переименовали или объединили, старое
название запоминается — сбор, присылающий «Отель», попадёт в «Отели».
Признаки и заготовка первой фразы пока тоже написаны под бронирование.

### Скрытые лиды

Компания закрылась или не подходит — кнопка **«Скрыть из списка»** внизу карточки
с необязательной причиной. Лид остаётся в базе, но пропадает из работы и из всех
счётчиков. Посмотреть убранное — фильтр «Только скрытые», вернуть — кнопка в карточке.

### Автопроверка через чат с Claude

Отдельный шаг между «Новым» и «Ручной проверкой». Обращений к API здесь нет —
проверку делает человек в чате, сервис только готовит запрос и принимает ответ.

```
Новый  →  [проверка в чате]  →  Автопроверка  →  [человек сверил]  →  Ручная проверка
```

В карточке кнопка **«Проверка»** открывает два шага:

1. **Запрос** — готовый текст с данными объекта, копируется одной кнопкой.
   Вставляется в чат с Claude, где включён поиск в интернете.
2. **Ответ** — сюда вставляется JSON из чата. Разбор терпим к обёртке:
   ответ может прийти в блоке ```json или с текстом вокруг.

Что спрашивается: работает ли бизнес, какой у него действующий сайт, через
какие площадки идут брони, контакты руководителя и проблемы с онлайн-присутствием.

**Против выдумок.** В самом запросе прописано: писать только то, что видел
в выдаче, давать ссылку на каждый факт, не нашёл — `null`. Найденное лежит
в отдельных полях `ai_*` и показывается с пометкой «находки поиска,
а не проверенные данные» и списком источников.

**Что не перезаписывается.** Контакты ставятся только в пустые поля и
помечаются источником «Claude». Ручные правки не трогаются. Адрес сайта
меняется только если своего рабочего нет. Руководитель из поиска попадает
в `ai_director`, а не в реестровое поле `director`: последнее принадлежит
ЕГРЮЛ и очищается при каждой сверке.

### Мой приоритет

Отдельная оценка **от 1 до 10**, которую ставит человек, просматривая сайты
подряд. Это не то же самое, что расчётный балл: балл говорит, насколько плох
сайт, приоритет — кому звонить раньше.

Ставится одним кликом по кнопке в карточке, снимается кнопкой «—».
Оценка видна в таблице отдельной колонкой «Мой», участвует в сортировке
(«по моему приоритету» — неоценённые уходят в конец, внутри равных оценок
порядок по расчётному баллу) и попадает в выгрузку CSV. Выгрузка соблюдает
тот же порядок, что выбран на экране.

### Правка карточки

Кнопка **«Изменить»** в шапке карточки открывает форму со всеми полями,
которые имеет смысл поправить руками:

- **Объект** — название, категория, адрес
- **Контакты** — телефон, Telegram, ВКонтакте, WhatsApp, почта
- **Реквизиты** — название в реестре, ИНН, ОГРН, руководитель, должность,
  ОКВЭД, юридический адрес

Телефон приводится к общему виду, `@` у Telegram и лишний путь у ссылки
ВКонтакте отбрасываются. Балл пересчитывается сразу: контакты на него влияют.

Каждое исправленное поле попадает в `manual_fields`, и **сбор его больше не
перезаписывает** — защита точечная, остальные поля продолжают обновляться
автоматически. В карточке видно, что именно исправлено; кнопка
«Вернуть автозаполнение» снимает защиту со всех полей лида.

### Смена адреса сайта

Если компания переехала на новый домен, адрес правится прямо в карточке.
При сохранении:

- прежняя ссылка остаётся в `previous_website` и показывается в карточке зачёркнутой;
- лид сразу перепроверяется по новому адресу, признак и балл пересчитываются;
- контакты, снятые со **старого** сайта, сбрасываются — к новому они отношения
  не имеют; контакты из OSM и ЕГРЮЛ сохраняются;
- выставляется `website_manual`, и **сбор больше не перезаписывает этот адрес** —
  иначе следующий прогон вернул бы мёртвую ссылку из OSM.

Кнопка «Перепроверить сайт» рядом прогоняет аудит заново, ничего не меняя в адресе.

## Конверсии и показатели

Раздел `/metrics`, доступен только владельцу базы. По нему ставятся планы,
считается вознаграждение продажнику, раскладываются деньги по конвертам и
принимается решение о найме. Продажник пункта меню не видит, со страницы его
возвращает на список, а `/api/metrics` отвечает ему 403.

Все расчёты живут в [metrics.py](metrics.py), фронтенд только рисует.
Дублировать формулы в двух местах нельзя: по этим цифрам платят людям.

### Про время

В базе три разных представления дат, и путать их нельзя:

| Где | Что лежит | Как сравнивается |
|---|---|---|
| `calls.ts`, `history.ts` | unix-время UTC | границами местных суток |
| `payments.paid_at`, `deals.contract_at` | ISO-дата, введённая человеком | строкой |
| `leads.created_at` | ISO-дата-время от сервера | строкой |

Суточные и месячные группировки делаются со сдвигом `TZ_OFFSET_HOURS`, иначе
звонок в 23:30 уехал бы в следующий день.

### Период и сравнение

Переключатель: эта неделя, этот месяц, прошлый месяц, квартал, произвольный
диапазон. Готовые периоды считает сервер — у него часовой пояс города, а
браузер владельца может стоять где угодно.

Рядом с каждым числом — изменение к предыдущему периоду такой же длины. Если
в прошлом периоде был ноль, стрелка не рисуется: рост «с нуля» в процентах не
выражается, и «+100 %» там было бы враньём.

### Воронка

Даты переходов берутся из журнала, где `action='status'` — это единственное
место, где хранится момент перехода: в `leads` лежит только текущий статус.
Считаются лиды, а не записи: вернуть лид в статус и снова из него — не два лида.

| Этап | Откуда |
|---|---|
| Лидов в базе | `leads` на конец периода, плюс добавлено за период |
| Ручная проверка | переходы в `in_work` |
| Попыток дозвона | строки `calls` за период |
| Дозвонились | уникальные лиды с `outcome='answered'` |
| Согласились на аудит | переходы в `audit` |
| Отправлено КП | переходы в `proposal` |
| Сделок закрыто | лиды, по которым в периоде прошёл первый платёж |
| Отказов | переходы в `refused` |

**Процент дозвона** считается по лидам, а не по звонкам: десять попыток до
одного человека — это один дозвон, а не десять шансов. Сквозная конверсия —
«ручная проверка → сделка». Воронка нарисована инлайновым SVG, внешних
библиотек на странице нет.

### Деньги

- **Поступило** — сумма `payments` по `paid_at` в периоде, с разбивкой на
  новые и повторные сделки по `deals.is_repeat`.
- **Средний чек** — средняя `amount` по сделкам, у которых первый платёж
  пришёлся на период.
- **Доля первой оплаты** — средняя по проектам. У абонентки `amount` это
  месячный платёж, а не цена договора, и делить на него бессмысленно.
- **Цикл сделки** — медиана числа дней от первого звонка по лиду до первого
  поступления. Медиана, а не среднее: одна затянувшаяся сделка перекосила бы
  среднее. Если платёж стоит раньше первого звонка, сделку завели задним
  числом без истории обзвона — цикл по ней неизвестен, и в расчёт она не идёт.
- **MRR** — сумма `amount` по активным сделкам `kind='retainer'`.
- **Доля клиентов на абонентке** — лиды с абонентской сделкой к лидам со
  сделками вообще.

### Вознаграждение продажника

Считается от **фактически поступивших** сумм, а не от цены договора — так
записано в договоре. По каждому продавцу:

```
вознаграждение = поступило по новым × ставка_новых
               + поступило по повторным × ставка_повторных
               + премия
```

Премия зависит от числа сделок, закрытых в периоде, и только тех, где доля
первой оплаты не ниже порога. Премии **не суммируются** — берётся одна,
наибольшая из достигнутых. Порог первой оплаты — условие из договора на
разовую разработку; к абонентке оно неприменимо, там первый платёж это целиком
первый месяц, и сравнивать его с «ценой договора» не с чем.

Рядом — срок выплаты до 10 числа следующего месяца, с заметной пометкой, если
осталось меньше пяти дней или срок уже прошёл.

### Конверты

Каждое поступление раскладывается по долям. Суммы долей обязаны давать ровно
100 — иначе раскладка молча перестаёт сходиться с выручкой, поэтому проверка
стоит и при вводе, и при сохранении.

Округление — по наибольшему остатку: целые части, а копеечный хвост достаётся
тем долям, у кого дробная часть была больше. Обычное округление каждой доли
дало бы расхождение, а конверты должны сходиться с поступлениями **до рубля**.

Показывается пришедшее за период и накопленное с начала ведения базы. У
конвертов «Производство» и «Сопровождение» рядом видно, хватает ли накопленного
на три месяца работы роли: пока человека не взяли, конверт копится, и важно не
«сколько там лежит», а «на сколько месяцев этого хватит».

### Триггеры найма

Светофор: зелёный — можно брать, жёлтый — поток есть, но денег в конверте нет,
серый — рано. Поток и деньги разведены намеренно: нанимать без трёхмесячного
запаса нельзя, даже когда заявок хватает.

| Роль | Правило |
|---|---|
| Пресейл-аккаунт | не меньше 3 сделок в месяц два месяца подряд |
| Контекстолог | не меньше 3 активных абонентских сделок |
| Разработчик | 5–6 проектов в месяц два месяца подряд |
| Второй продажник | производство держит двойной поток |
| Маркетолог | MRR не ниже 150 000 ₽ |

Текущий месяц в «месяцах подряд» не считается: он ещё не кончился, и судить по
нему рано. Отдельной даты сдачи проекта в базе нет, поэтому «сдан» считается
по сделкам в состоянии «готово».

### Лимит НПД

Поступления за скользящие 12 месяцев против лимита 2 400 000 ₽, полоса
заполнения и прогноз даты исчерпания при текущем среднемесячном темпе.
Скользящие 12 месяцев, а не календарный год: так приближение видно заранее,
а не 31 декабря. После 70 % — предупреждение, что пора открывать ИП.

### Настройки

Ставки, пороги премий, доли конвертов, стоимости ролей, пороги найма и лимит
НПД лежат в таблице `settings`, а не в коде: договор с продажником прямо
предусматривает их пересмотр, и менять это должен владелец через интерфейс,
а не правка исходников с деплоем. Значения хранятся строками JSON — так в
одной таблице уживаются и числа, и словари долей.

Правки пишутся в журнал с действием `settings`. Недостающий ключ не роняет
раздел: используется значение по умолчанию из `db.DEFAULT_SETTINGS`.

| Ключ | По умолчанию |
|---|---|
| `rate_new` | 20 % |
| `rate_repeat` | 10 % |
| `first_share_min` | 30 % |
| `bonus_levels` | 8 000 ₽ от 6 сделок, 20 000 ₽ от 10 |
| `envelopes` | Продажи 20, Производство 25, Сопровождение 10, Налоги 7, Операционка 5, Резерв 10, Владелец 23 |
| `role_costs` | Производство 60 000 ₽/мес, Сопровождение 40 000 ₽/мес |
| `npd_limit` / `npd_warn` | 2 400 000 ₽ / 70 % |

### Активность команды

За период по каждому сотруднику: заведено лидов, звонков, дозвонов, процент
дозвона, заметок, смен статуса. Автор-автомат `@system` в отчёт не попадает —
иначе перенесённые заметки и записи сбора числились бы за несуществующим
человеком. Оттуда же ссылка на страницу «Рабочее время».

## Настройка

### Кто может входить

Своя страница входа, сессия живёт 30 дней. Пользователи задаются
переменной `LEADGEN_USERS` — логин и пароль через двоеточие,
пользователи через точку с запятой:

```bash
LEADGEN_USERS=andrey:пароль;marketolog:другой-пароль
```

На сервере это `/etc/leadgen.env` (права 600, в репозиторий не попадает).
После правки — `systemctl restart leadgen`.

Пароль можно держать не открытым текстом, а хэшем:

```bash
python auth.py hash мой-пароль
# LEADGEN_USERS=andrey:pbkdf2$200000$соль$хэш
```

После семи неудачных попыток подряд адрес блокируется на пять минут.

### Dadata (необязательно, но желательно)

Регистрация на <https://dadata.ru>, ключ в профиле. Затем:

```bash
set DADATA_TOKEN=ваш_токен        # Windows
export DADATA_TOKEN=ваш_токен     # Linux
```

Без токена источник просто пропускается, OSM работает сам по себе.

### Другой город или ниша

Всё в [config.py](config.py):

- `CITY_NAME`, `CITY_BBOX` — город и рамка поиска (bbox берётся с запасом,
  чтобы захватить пригород с базами отдыха)
- `OSM_FILTERS` — какие теги OSM считаем нашей нишей
- `DADATA_QUERIES`, `NICHE_OKVED_PREFIXES` — как ищем в ЕГРЮЛ
- `OUTDATED_YEARS` — с какого возраста копирайт считается устаревшим

## Боевой сервер и автодеплой

Работает на <https://leadgen.kahman.studio> под базовой авторизацией nginx.

| Что | Где |
|---|---|
| Код | `/opt/leadgen` (git-репозиторий, ветка `main`) |
| Окружение | `/opt/leadgen/venv` |
| База лидов | `/var/lib/leadgen/leads.db` — **вне репозитория**, деплой её не трогает |
| Кеш Overpass | `/opt/leadgen/.cache` |
| Секреты | `/etc/leadgen.env` (там же `DADATA_TOKEN`) |
| Сервис | `systemctl status leadgen`, логи — `journalctl -u leadgen -f` |
| nginx | `/etc/nginx/sites-available/leadgen.kahman.studio` |
| Пользователи | `LEADGEN_USERS` в `/etc/leadgen.env` |

Приложение слушает только `127.0.0.1:8765` — снаружи в него можно попасть
исключительно через nginx, то есть только с паролем.

### Как работает автодеплой

```
git push origin main
   ↓
GitHub Actions (.github/workflows/deploy.yml)
   ↓  ssh root@сервер 'bash -s' < deploy/deploy.sh
   ↓
git fetch + reset --hard origin/main → pip install → systemctl restart leadgen
```

Скрипт деплоя передаётся по stdin, а не запускается с сервера: иначе bash читал бы
файл, который git прямо в этот момент переписывает.

`git reset --hard` затрагивает только отслеживаемые файлы, поэтому база,
кеш и `venv` переживают деплой.

Конфиг nginx едет вместе с кодом: деплой копирует `deploy/nginx-leadgen.conf`,
проверяет его через `nginx -t` и перезагружает nginx. Если проверка не прошла,
прежний конфиг возвращается на место — соседние сайты на том же nginx
сломаться не могут.

Единственный секрет в GitHub — `DEPLOY_KEY`, приватный SSH-ключ для входа
на сервер. Адрес сервера секретом не является и лежит в самом workflow.

Деплой можно запустить и вручную: вкладка **Actions → Деплой на сервер → Run workflow**.

### Первичная настройка с нуля

Если сервер поднимается заново — всё делает один скрипт:

```bash
bash deploy/bootstrap.sh
```

Он ставит пакеты, создаёт системного пользователя `leadgen`, клонирует репозиторий,
собирает venv, генерирует пароль, выпускает сертификат Let's Encrypt и включает сервис.
Повторный запуск безопасен.

### Ручные команды

```bash
ssh root@130.49.146.66 'bash -s' < deploy/deploy.sh   # выкатить вручную
ssh root@130.49.146.66 'journalctl -u leadgen -n 50'  # посмотреть логи
ssh root@130.49.146.66 'systemctl restart leadgen'    # перезапустить
```

Завести или сменить пользователя:

```bash
nano /etc/leadgen.env        # LEADGEN_USERS=логин:пароль;логин2:пароль2
systemctl restart leadgen

## Почему сервиса нет в поиске

- `robots.txt` отдаёт `Disallow: /` для всех роботов;
- заголовок `X-Robots-Tag: noindex, nofollow, noarchive, nosnippet` на каждом ответе;
- тот же запрет мета-тегом на страницах;
- без входа отдаётся только форма логина — индексировать попросту нечего.

**Чего это не даёт.** Само существование поддомена скрыть нельзя: при выпуске
сертификата Let's Encrypt имя попадает в публичные логи Certificate Transparency,
и адрес можно найти там. Защита от этого — не секретность имени, а вход по паролю.

## Правовые рамки

**Сбор.** Данные OSM под ODbL, ЕГРЮЛ — открытые сведения. Хранить можно.

**Касание — здесь осторожно.** Ст. 18 38-ФЗ: реклама по сетям связи без
предварительного согласия запрещена, штраф для юрлица 100–500 тыс. рублей,
ФАС работает по жалобам.

На практике разница такая:

- ❌ массовая рассылка «закажите сайт» по собранным адресам — прямой риск
- ✅ живой персональный звонок с конкретной проблемой клиента

Поэтому сервис и заточен под **20 точных касаний с поводом**, а не под выгрузку
тысяч адресов в рассыльщик. Поле `pitch` — это всегда проблема клиента,
а не наш оффер.
